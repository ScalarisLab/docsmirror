# DocsMirror, how to read and write `@docs` pointers

For a tool with its own skill system (for example Claude Code), place this file, frontmatter
included, where that tool expects a skill: Claude Code looks for `.claude/skills/docsmirror/SKILL.md`
in the repository. For everything else, append the body below the frontmatter to your project's
agent instructions, `AGENTS.md`, `CLAUDE.md`, `.cursorrules`, or your own system prompt, so any
coding agent handles the convention correctly.

## What a pointer is

A comment in this codebase may carry a pointer instead of a long explanation:

```ts
/**
 * Retries are safe here: the endpoint is idempotent by design.
 * @docs decisions/retry-policy.md#idempotency
 */
```

`@docs <path>#<anchor>` means: *the reasoning behind this code lives in that document, in that
section.* The one-line comment above it is the claim; the document is the justification.

## Start with the manifest

Before reading any documentation, look for **`docsmirror.json`** at the project root. It is a
generated map of the entire documentation surface: every document, a one-line summary of what it
covers, every section anchor, and which code points at each one.

Use it to *choose*, then read only what you chose:

- "What does this project document about caching?" → scan the manifest's `summary` and `anchors`
  fields, open the one document that matches. Do not read the folder.
- "What depends on this decision?" → read that node's `referencedBy`: each entry is a real
  `@docs` pointer, with the file, the line, and often the symbol name.
- If the project exposes the DocsMirror **MCP server**, prefer its tools, `list_documentation` to
  discover, `search_documentation` to find, `read_documentation` to read one section,
  `find_references` to see what depends on it. Same map, fetched properly.

If there is no `docsmirror.json`, the pointers in the source still work exactly as described below;
you have just lost the index, so be more conservative about how much you read.

Never edit `docsmirror.json` by hand. It is generated by `docsmirror manifest`, and
`docsmirror check` fails when it has drifted from the documentation on disk. If you change
documentation, regenerate it rather than patching it.

## Reading a pointer

1. **The path is relative to the project's docs root**, not to the file you are reading, and not to
   the repository root. The docs root is `docs/` unless `docsmirror.config.json` sets `docsRoot` to
   something else, check that file once, then resolve every pointer against it.
   `@docs decisions/retry-policy.md#idempotency` means `docs/decisions/retry-policy.md`.
2. **The anchor is a GitHub-style heading slug.** `#idempotency` is the section whose heading
   slugifies to `idempotency`, for example `## Idempotency`. The section is that heading and
   everything under it, subsections included, up to the next heading of the same or higher level.
   An extension-less path such as `@docs decisions/retry-policy` means the `.md` file of that name.
3. **The anchor is optional.** A bare `@docs architecture.md` points at the whole document.

## When to fetch the document

Read the target document when the pointer is relevant to the task in front of you, you are about
to change the behaviour the comment describes, you need to know why a rule exists, you are asked
whether something is intentional, or a reviewer's question turns on the reasoning rather than the
code. Read the pointed-to section, not the whole documentation tree.

Do not fetch documents that are merely nearby. The point of the convention is that you pay for the
prose only when you need it; loading every document a file mentions rebuilds the exact problem it
was designed to remove.

**Never contradict a document you have not read.** If a pointer covers the decision you are about
to change, read it first. If the code and the document disagree, say so explicitly rather than
silently picking one: one of them is a bug, and which one is a decision for a human.

## When you write a long explanation

If your answer or your change needs more than about three lines of comment to justify itself, that
text belongs in the documentation, not in the source file:

1. Write it in the docs root, extend an existing document if one already covers the subject, and
   only create a new file if none does.
2. Give it a heading you can anchor to.
3. Leave a short comment in the source, one line of claim plus the pointer:

```ts
/**
 * Requests are batched per tenant, never globally.
 * @docs decisions/batching.md#per-tenant-batches
 */
```

Prefer extending an existing document over creating a new one; a docs folder that grows one file
per thought is as unusable as no docs at all.

## When you move or rename things

- Moving a **source file** never breaks a pointer: the path is docs-root-relative on purpose.
- Renaming a **document** or changing a **heading** breaks every pointer aimed at it. Update the
  pointers in the same change.
- `docsmirror check` reports both failures. Run it after editing documentation or pointers, and
  treat a failure as a real error, never as noise to suppress.

## What not to do

- Do not write `@docs` with a markdown link, an absolute path, a URL, or a `../` path. Only a bare
  docs-root-relative path is valid.
- Do not invent a pointer to a document that does not exist yet. Write the document first.
- Do not delete a pointer because you could not resolve it. A broken pointer is a signal that
  something moved; fix the target or the path.
- Do not restore a long explanatory comment "for clarity" next to a pointer. The pointer is the
  clarity.
